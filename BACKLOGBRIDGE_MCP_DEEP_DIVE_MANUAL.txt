1. EXECUTIVE SUMMARY & ELEVATOR PITCH
----------------------------------------------------------------------------------------------------

1.1 30-Second Elevator Pitch
BacklogBridge-MCP is a lightweight, local-first issue tracker and project management engine
specifically engineered for autonomous AI coding agents (Claude Code, Cursor, OpenCode, Windsurf, Zed)
and human engineering teams. Built in Rust 2024 and compiled to a single self-contained ~25MB binary,
it integrates deeply with Anthropic's Model Context Protocol (MCP) using a hyper-compact 31-tool suite
that consumes only ~5,781 tokens. It replaces transient, hallucination-prone LLM context windows with
persistent, ACID-compliant SQLite storage, sub-millisecond query execution, and real-time human-in-the-
loop visibility.

1.2 2-Minute Deep Technical Summary
Modern software engineering is transitioning from manual programming to agentic workflows where
multiple AI models work concurrently across feature branches. However, traditional project management
tools (Jira, Linear, GitHub Issues) were built exclusively for human clicks and REST/GraphQL APIs with
huge payloads, complex auth flows, and 100-300ms network latencies. Conversely, naive text-based
workarounds (like keeping a TODO.md in the git tree) result in git merge conflicts, split-brain states
between competing agents, and no real-time auditability.

BacklogBridge-MCP introduces an agent-native data and protocol layer:
1. Native MCP Integration: Supports both local zero-overhead 'stdio' pipes (ideal for single-developer
   local CLI workflows) and remote 'Streamable HTTP' (Server-Sent Events + JSON-RPC) for hosted team
   environments.
2. Token-Engineered Schema: While typical MCP servers consume 15,000+ tokens just loading tool definitions,
   BacklogBridge-MCP fits 31 complete, polymorphic tools into ~5,781 tokens.
3. Surgical Data Mutation: Tools such as `edit_issue` and `edit_page` utilize exact string replacement
   (`old_string` -> `new_string`) instead of streaming entire descriptions back and forth, saving
   millions of tokens over a multi-day sprint.
4. Deterministic Concurrency Engine: Written in Rust on top of Axum 0.8 and Tokio, utilizing SQLite in
   Write-Ahead Logging (WAL) mode with a custom read/write splitting pool (1 dedicated writer mutex,
   lock-free reader queue).
5. Observability & Attribution: Every action taken by an AI model is mapped to a dedicated bot identity
   bound cryptographically to its human owner, providing a tamper-proof audit log with real-time
   WebSocket updates delivered to a reactive Svelte 5 frontend.

1.3 Key Architectural Metrics & Vital Statistics
- Core Language: Rust (2024 Edition, rustc 1.88+)
- Backend Framework: Axum 0.8, Tokio 1.0 (multi-thread runtime), Tower-HTTP
- Storage Engine: Embedded SQLite 3.45+ (WAL mode, foreign keys enabled, normal synchronous)
- Binary Footprint: ~25 MB to ~32 MB (statically linked, frontend assets embedded via rust-embed)
- Memory Footprint: Idle RSS ~18 MB; under heavy concurrent agent load ~45-65 MB
- MCP Toolset: 31 tools registered via `rmcp` 1.4 macros
- Token Overhead: Exactly ~5,781 tokens for all 31 tool definitions combined
- Web UI: Svelte 5 (Runes reactivity system), Tailwind CSS v4, Vite 8, Lucide icons
- Realtime Engine: WebSocket (RFC 6455) + Server-Sent Events (SSE) with tungstenite backpressure control
- Cold Startup Time: < 15 milliseconds on modern NVMe drives
- Disaster Recovery: Continuous hot backups via `fs2` advisory locking; streaming tar.gz archive dump/restore

2. THE CORE PROBLEM STATEMENT: WHY AGENTIC WORKFLOWS FAIL
----------------------------------------------------------------------------------------------------

2.1 The LLM Context Window Paradox (Transient Memory vs. Large-Scale Codebases)
LLMs possess finite context windows (e.g., 128k, 200k, or 1M tokens). However, "effective context"
(the needle-in-a-haystack retrieval performance and reasoning coherence) degrades precipitously as
the prompt fills up.
When developers use autonomous agents (e.g., Claude Code, Cursor Composer, Devin), the standard
approach is to stuff the task description, architecture notes, step plans, and previous test logs
into the system prompt.
This creates three fatal problems:
a) Context Starvation: The more context consumed by backlog and status bookkeeping, the less context
   remains for actual source code, syntax trees, compiler error messages, and documentation.
b) Amnesia on Session Expiration: When an agent hits its token limit or the user resets the session,
   all historical progress, blockers encountered, and remaining sub-tasks vanish completely.
c) Hallucinatory Drifting: Without an external system of record, an agent in a prolonged loop forgets
   initial constraints and begins modifying unrelated code.

2.2 The Multi-Agent Coordination Dilemma (Split-Brain & State Desynchronization)
When multiple agents work on a single repository simultaneously (e.g., Agent A refactoring the database
schema while Agent B implements an API endpoint and Agent C writes end-to-end integration tests):
- If coordination is kept in LLM memory, Agent A and Agent B have zero mutual awareness.
- If coordination is stored in a file in git (e.g., `TODO.md` or `tasks.json`), both agents attempt to
  commit edits to the same lines, causing immediate git merge conflicts, corrupted markdown, or broken
  rebases.
- Race Conditions: Two agents might pick up the exact same issue simultaneously, duplicating effort
  and wasting expensive API tokens.

2.3 The Verification & Proof Vacuum (Hallucination vs. Provable Progress)
Autonomous coding agents frequently report tasks as "complete" when in reality the code fails to compile,
tests fail silently, or edge cases were ignored.
In BacklogBridge-MCP, task completion is treated as a verifiable state transition:
- An issue cannot simply be marked `done` without an audit trail.
- Agents are incentivized and instructed via tool contracts to attach verification evidence (such as
  terminal output from `cargo test`, linters, or coverage reports) directly to comments or plan steps.
- Human engineers can inspect the exact command outputs, timestamps, and git commits attached to the
  ticket before approving deployment.

3.2 Honest Trade-Off Analysis: When NOT to Use BacklogBridge-MCP
As a software engineer, you must never claim a technology is a silver bullet. Here is when BacklogBridge-MCP
is the wrong choice:
1. Massive Non-Technical Enterprise Organizations: If an organization has 5,000 non-technical stakeholders
   (HR, Legal, Sales, Marketing) who require complex Gantt charts, advanced billing timesheets, and
   Salesforce integrations, Jira or ServiceNow is appropriate.
2. Pure Human Teams with Zero AI Agent Tooling: If a engineering team does not use Claude Code, Cursor,
   Windsurf, or automated agent pipelines, Linear provides a more polished ecosystem for human-only teams.
3. Multi-Region Distributed Master-Master Replication: BacklogBridge-MCP is designed around a single-node
   SQLite model (with hot replicas and backups). If your architecture mandates active-active multi-region
   write replication across continents, a distributed database like CockroachDB or Spanner is needed.

3.3 The Token Economy & Query Latency Benchmark
Why does a low token count and sub-millisecond query speed matter in AI engineering?
- Token Cost: If an agent runs 200 turns a day using Claude 3.5 Sonnet ($3 / million input tokens):
  * Linear MCP (~14,000 tool tokens): Injected every turn -> 200 * 14,000 = 2,800,000 tokens = $8.40 / day / agent.
  * BacklogBridge-MCP (~5,781 tokens): Injected every turn -> 200 * 5,781 = 1,156,200 tokens = $3.46 / day / agent.
  * Annual savings across a team of 10 autonomous agents = Over $18,000 USD purely in prompt overhead!
- Latency Overhead:
  * Over standard stdio pipes, BacklogBridge-MCP processes queries against SQLite in 0.4 milliseconds.
  * Over cloud APIs, an agent waits 200-500ms per tool call. In a multi-step task involving 20 queries,
    the cloud agent wastes 10 seconds waiting on network packets alone.

4.2 Dual-Transport Protocol Pipeline: stdio vs. Streamable HTTP (SSE)
BacklogBridge-MCP is protocol-bilingual:
1. stdio Transport:
   - Used when launching an agent locally via `backlogbridge-mcp mcp --db backlog.db`.
   - Communication occurs over standard input and standard output file descriptors (stdin/stdout).
   - Zero networking stack: no TCP handshake, no TLS encryption, zero port conflicts, immune to firewall
     rules.
   - Ideal for single-tenant local agents (Claude Desktop, Cursor local MCP).
2. Streamable HTTP Transport:
   - Used when running as a daemon or server via `backlogbridge-mcp start --port 3456`.
   - Implements MCP over HTTP POST for client requests, coupled with Server-Sent Events (SSE) for
     asynchronous server-to-client notifications.
   - Fully secured with Bearer API tokens (`Authorization: Bearer lific_sk-live-...`).
   - Enables centralized backlog management across remote engineering clusters.

4.4 Real-Time Synchronization & Multi-Tab Web Lock Leader Election
In modern browser environments, a user might open 10 tabs of BacklogBridge-MCP simultaneously.
Naive web applications open 10 concurrent WebSocket connections to the server, multiplying server
tasks, memory buffers, and database polling by 10x.
BacklogBridge-MCP solves this elegantly on the client:
- Web Locks API (`navigator.locks.request("merge-sync", ...)`):
  * All browser tabs compete for a shared web lock named `merge-sync`.
  * Exactly ONE tab becomes the "Leader Tab" and opens a single persistent WebSocket to the backend.
  * The Leader Tab relays incoming events to all other tabs via a `BroadcastChannel` ("merge-sync-events").
  * If the user closes the Leader Tab, the browser instantly transfers the lock to another tab, which
    seamlessly establishes the WebSocket connection with zero loss of real-time events.

5. EXHAUSTIVE TECH STACK AUDIT: CHOICES, ALTERNATIVES & JUSTIFICATIONS
----------------------------------------------------------------------------------------------------

5.1 Core Language: Rust 2024 Edition
- Chosen Because:
  * Zero-Cost Abstractions & Fearless Concurrency: Allows handling thousands of concurrent MCP queries
    and WebSocket connections on a single thread pool without garbage collection pauses.
  * Memory Safety Without GC: Autonomous coding agents generate high volumes of short-lived JSON-RPC
    strings. In garbage-collected languages (Java, Go, Node.js), this triggers frequent GC cycles
    causing latency spikes. In Rust, RAII and deterministic deallocation guarantee consistent sub-millisecond
    response times.
  * Static Binary Compaction: Rust compiles down to a single bare-metal machine code binary with zero
    runtime dependencies (no Node runtime, no Python virtualenv, no JVM).
- Alternatives Considered & Rejected:
  * Go: Go's runtime GC introduces non-deterministic stop-the-world pauses. Go lacks sum types (enums
    with data) and expressive compile-time macro metaprogramming, which would make implementing the
    polymorphic MCP tool router significantly more verbose and prone to runtime bugs.
  * Node.js / TypeScript: Highly susceptible to dependency rot (thousands of `node_modules`), heavy
    memory footprint (150MB+ RSS minimum), and single-threaded event loop bottlenecks during CPU-intensive
    tasks (like calculating line diffs or streaming large project archives).
  * Python: Too slow for sub-millisecond database/protocol handling; distribution requires Python runtime
    matching; lack of static typing at compile time invites runtime errors.

5.2 Asynchronous Runtime: Tokio (Multi-Threaded Worker Pool)
- Chosen Because:
  * Industry standard for high-performance network services in Rust.
  * Configured with `bounded_worker_threads` (clamped between 1 and 8 worker threads) so that on 64-core
    server chips, the runtime does not spawn an unnecessary swarm of worker threads for an I/O-bound tool.
  * Seamless integration with `tokio::sync::broadcast` for fan-out realtime event buses and `tokio::task_local!`
    for carrying security contexts across asynchronous task boundaries.
- Alternatives Considered & Rejected:
  * async-std: Smaller ecosystem; lacks the mature HTTP/Tower middleware integration available in Tokio.
  * Single-threaded Tokio runtime: Would stall concurrent MCP queries during background SQLite writes or
    large file streaming.

5.3 HTTP & WebSocket Engine: Axum 0.8 + Tower-HTTP
- Chosen Because:
  * Ergonomic type-safe extractors: Authentication, path parameters, and JSON payloads are validated at
    compile time. If an endpoint expects an `AuthUser`, Axum guarantees the request cannot execute unless
    the extractor succeeded.
  * Built directly on Hyper 1.0 and Tower service abstractions, providing battle-tested HTTP/1.1 and HTTP/2
    support with native CORS, gzip, and brotli compression layers.
  * Native WebSocket support via `axum::extract::ws::WebSocket` using `tokio-tungstenite`.
- Alternatives Considered & Rejected:
  * Actix-web: Uses an actor-system legacy design which adds conceptual complexity and architectural friction
    when sharing async SQLite connection pools across handlers.
  * Rocket: Slower development velocity; historically heavily reliant on nightly Rust compiler features.

5.4 Protocol Layer: rmcp 1.4 (Model Context Protocol Specification)
- Chosen Because:
  * Official Rust SDK implementing Anthropic's Model Context Protocol.
  * Pinning Strategy (`~1.4`): MCP is evolving rapidly. Minor version bumps in `rmcp` (e.g., 1.7 to 1.8)
    introduced breaking changes to JSON-RPC error constructors and tool parameter validation. Pinning to
    `~1.4` guarantees build reproducibility across diverse developer machines and CI/CD pipelines.
- Alternatives Considered & Rejected:
  * Writing Custom JSON-RPC 2.0 Parser: Unnecessary reinvention of the wheel that risks drifting out of
    compliance with Anthropic's official client specifications.

5.5 Database Architecture: Embedded SQLite (WAL Mode + Custom Read/Write Pool)
- Chosen Because:
  * Local-First Simplicity: Zero external servers to install, configure, or administer. No `docker run postgres`.
  * Embedded Speed: Database queries are in-process function calls reading directly from local memory/disk,
    bypassing TCP networking overhead entirely.
  * ACID Compliance: Full transactional safety with Write-Ahead Logging (WAL).
- Alternatives Considered & Rejected:
  * PostgreSQL: Adds massive operational friction (requires network ports, credentials, daemon management).
    Makes local single-binary CLI distribution impossible.
  * DuckDB: Optimized for OLAP (analytical queries over columnar data), whereas issue tracking is strictly
    an OLTP workload (frequent point reads, indexed lookups, and single-row updates).
  * RocksDB / Key-Value Stores: Lacks declarative SQL queries, foreign key relational constraints, and
    secondary indexing, requiring manual implementation of join logic and search indexes.

5.6 Web Frontend: Svelte 5 (Runes) + Tailwind CSS v4 + Vite + Bun
- Chosen Because:
  * Svelte 5 Runes (`$state`, `$derived`, `$effect`): Compiles down to minimal, surgically precise vanilla
    JavaScript without a Virtual DOM overhead. Bundle size is a fraction of React.
  * Tailwind CSS v4: Delivers lightning-fast CSS compilation and modern color-scheme/dark-mode primitives.
  * Embedded UI: The entire frontend compiles into `web/dist/` and is baked into the Rust binary, serving
    the web app instantly from RAM with zero file-system latency.
- Alternatives Considered & Rejected:
  * React 19 / Next.js: Enormous bundle sizes (several megabytes of JavaScript runtime), slow initial render,
    and heavy node-server dependencies incompatible with a self-contained single binary.
  * HTMX: Good for traditional server-rendered apps, but incapable of providing the smooth drag-and-drop
    Kanban board interactions, optimistic UI updates, and real-time canvas diagrams required by modern devs.

5.7 Cryptography & Auth Architecture
- Argon2id (`argon2` crate): Memory-hard password hashing function, resistant to GPU/ASIC brute-force
  attacks, used for securing human administrator accounts.
- Constant-Time Comparison (`subtle::ConstantTimeEq`): All API keys, session tokens, and OAuth device
  codes are checked using constant-time string comparisons to eliminate timing side-channel attacks.
- SHA-256 Digesting: Raw bearer tokens are never stored in plaintext in the database. Only hex-encoded
  SHA-256 hashes are persisted.
- OS Keyring Integration (`keyring` crate): CLI credentials securely hook into macOS Keychain, Windows
  Credential Manager, and Linux Secret Service (via pure-Rust static libdbus), avoiding insecure plaintext
  disk storage whenever possible.

5.8 Disaster Recovery: Hot Atomic Snapshots & Advisory Locks

  backup, preventing disk thrashing and retention rotation corruption.

7. INTERNALS, CONCURRENCY & RELIABILITY ENGINEERING
----------------------------------------------------------------------------------------------------

7.1 Custom Read/Write Splitting Connection Pool & Deadlock Prevention
SQLite enforces a single-writer constraint at the database file level. In multi-threaded async runtimes,
naive SQLite pooling leads to `SQLITE_BUSY` contention errors and thread starvation.
BacklogBridge-MCP implements a custom `DbPool` architecture in `src/db/mod.rs`:
- Writer Channel: Exactly one `Arc<Mutex<rusqlite::Connection>>`. All mutation transactions acquire this
  mutex, guaranteeing that writes are serialized at the application layer before reaching SQLite.
- Reader Pool: An `Arc<ArrayQueue<rusqlite::Connection>>` holding 8 dedicated read-only connections.
  Reads pop a connection without acquiring locks against the writer.
- Under SQLite WAL mode (`PRAGMA journal_mode=WAL;`), readers and writers never block each other.
- RAII Safety: `ReadConn` implements `Deref<Target=Connection>` and `Drop`. When a read operation
  completes, the connection is automatically returned to the `ArrayQueue`. If the pool is saturated,
  the connection is cleanly closed.

7.2 Task-Local Context Transmission & Zero-Race Identity Propagation
In Axum, requests pass through asynchronous middleware pipelines. Passing user identities and bot tokens
down deep nested call stacks can cause synchronization hazards.
BacklogBridge-MCP leverages `tokio::task_local!`:
```rust
tokio::task_local! {
    static REQUEST_DATA: RequestData;
}
```
When an HTTP request or stdio frame is authenticated, its verified security principal (User, Bot Token,
Owner ID) is bound to the Tokio task future. Any tool executed downstream can instantly resolve its caller
identity without parameter passing or global state poisoning.

7.3 Bounded Realtime WebSocket Architecture (Tungstenite Buffer Protection)
WebSockets can easily be weaponized to trigger Out-Of-Memory (OOM) crashes by streaming unbounded data.
In `src/realtime.rs`, BacklogBridge-MCP enforces strict defensive bounds:
- `MAX_CLIENT_MESSAGE_BYTES`: Capped at 16 KB.
- `MAX_CLIENT_FRAME_BYTES`: Capped at 4 KB.
- `CLIENT_MESSAGE_WINDOW` & `MAX_CLIENT_MESSAGES_PER_WINDOW`: Rate-limited to 64 messages per 10 seconds.
- `SOCKET_SEND_TIMEOUT`: Capped at 5 seconds. If a client stalls and stops reading, the server drops the
  socket rather than pinning memory buffers.
- Concurrency Limits: Compile-time validated quotas (`MAX_SOCKETS_PER_USER = 16`, `MAX_SOCKETS_TOTAL = 1024`).

7.4 Multi-Process Advisory Locking for Zero-Impact Hot Backups
In `src/backup.rs`, continuous disaster recovery is coordinated across distinct OS processes:
- Multiple processes might be running against the same database: `backlogbridge-mcp start` (web server),
  `backlogbridge-mcp mcp` (stdio agent), and terminal CLI calls.
- To prevent redundant backup thrashing, BacklogBridge-MCP places an advisory lock file (`fs2::FileExt`)
  in the backup directory.
- Before running a backup, a process acquires an exclusive non-blocking file lock. If another process is
  already writing the snapshot, the second process gracefully skips the run.

7.5 Monotonic Sequence Protocol (`sync_seq`) & Conflict-Free Deltas
Every database mutation increments a global 64-bit integer (`sync_seq`).
When clients or agents reconnect after a network disconnect, they do not need to re-download the entire
backlog. They query:
`SELECT * FROM audit_log WHERE seq > ? ORDER BY seq ASC;`
This enables instantaneous delta synchronization with zero bandwidth waste.

9. ULTIMATE INTERVIEW DEFENSE: HARD & VERY HARD TECHNICAL QUESTIONS
----------------------------------------------------------------------------------------------------

This section provides rigorous, staff-level answers to 25 challenging interview questions spanning

----------------------------------------------------------------------------------------------------
GROUP A: DISTRIBUTED SYSTEMS & PROTOCOL DESIGN
----------------------------------------------------------------------------------------------------

Q1: "Why did you build an MCP server rather than exposing a standard REST or GraphQL API for agents?"
Answer:
"REST and GraphQL were designed for human user interfaces and microservices, not autonomous LLMs.
First, an LLM cannot natively 'browse' an arbitrary REST API without either hardcoded client code or
consuming thousands of tokens reading an OpenAPI specification on every turn.
MCP (Model Context Protocol) is an open standard that models tool capabilities as first-class JSON-RPC
primitives that AI clients (Claude, Cursor, Zed) natively negotiate during the handshake.
Second, GraphQL and REST payloads contain substantial syntactic bloat (headers, envelopes, metadata)
that consumes valuable context tokens.
Third, standard REST lacks native bidirectional protocol facilities for local process communication;
MCP natively defines both 'stdio' (zero-overhead Unix pipes) and 'Streamable HTTP' (SSE + JSON-RPC),
enabling identical agent tooling to run either inside a zero-network local terminal or across a hosted
cloud infrastructure."

Q2: "How does BacklogBridge-MCP achieve 31 tools within ~5,781 tokens when typical servers use 15k+ tokens?"
Answer:
"Through three deliberate architectural decisions:
1. Polymorphic Resource Consolidation: Instead of standard CRUD bloat where every entity has individual
   create/read/update/delete tools (e.g., `create_project`, `create_label`, `create_folder`), we consolidated
   lifecycle operations into polymorphic engines: `manage_resource` and `delete`. This eliminates redundant
   JSON-Schema declarations.
2. Parameter Minimization & Strict Typing: Schemas utilize compact, semantic enums and concise descriptions
   generated via `schemars` without verbose schema annotations.
3. Surgical Text Replacement: By implementing `edit_issue` and `edit_page` with `old_string`/`new_string`
   semantics, we avoided having to define complex multi-field patch payloads, keeping the schemas lean
   and maximizing the LLM's remaining context window for code generation."

Q3: "Explain how you prevent split-brain issues when multiple agents concurrently access the backlog."
Answer:
"Split-brain and race conditions are prevented at both the database and application layers:
1. Transactional Atomicity: All mutations go through a single serialized SQLite writer thread guarded by
   an `Arc<Mutex<Connection>>`. This guarantees that state changes (e.g., claiming a ticket) are atomic.
2. Workable Filter Semantics: The `workable=true` filter queries status and dependency graphs dynamically
   within an active transaction. When Agent A updates an issue to `in_progress`, that ticket is immediately
   invisible to Agent B's next `list_issues(workable=true)` query.
3. Dependency Graph Resolution: If an issue is marked with a `blocks` relationship, it cannot be claimed
   by any agent until the blocking parent is marked `done`. Circular dependencies are detected and rejected
   at insertion time using cycle-detection graph traversal."

Q4: "What is the difference between the stdio transport and the Streamable HTTP transport?"
Answer:
"The stdio transport operates directly over OS standard input/output pipes (file descriptors 0 and 1).
The client spawns the `backlogbridge-mcp` binary as a child process. Messages are serialized as newline-
delimited JSON-RPC 2.0 frames. It requires zero network ports, has zero socket overhead, has sub-millisecond
execution latency, and cannot be intercepted over a network.
The Streamable HTTP transport operates over HTTP/1.1 or HTTP/2 using Axum. The agent sends JSON-RPC requests
via HTTP POST to `/mcp`, and the server delivers asynchronous events and tool responses via Server-Sent
Events (SSE). This transport is authenticated via Bearer tokens and is designed for multi-user, multi-agent
hosted environments."

Q5: "How does the Leader Election mechanism work across multiple browser tabs?"
Answer:
"To prevent 10 open browser tabs from spawning 10 separate WebSocket connections and flooding the server,
we use the Web Locks API (`navigator.locks.request`).
All tabs in the same origin request an exclusive lock named `merge-sync`. The browser grants the lock to
exactly one tab (the Leader). The Leader opens the single WebSocket connection to `/ws`.
When messages arrive from the server, the Leader broadcasts them to the other tabs using a `BroadcastChannel`
named `merge-sync-events`.
If the Leader tab is closed or crashes, the browser automatically releases the lock and grants it to one
of the pending tabs, which instantly promotes itself, establishes a new WebSocket connection, and resumes
broadcasting seamlessly."

GROUP B: RUST INTERNALS, MEMORY SAFETY & CONCURRENCY
----------------------------------------------------------------------------------------------------

Q6: "Why did you choose Tokio over async-std or smol, and how did you configure the runtime?"
Answer:
"Tokio was chosen because it is the foundational bedrock of high-performance Rust networking, powering
Hyper, Axum, and Tower.
However, default Tokio multi-threaded runtimes spawn worker threads equal to the number of CPU cores.
On a 64-core machine, spawning 64 worker threads for an I/O-bound project tracker would waste significant
memory in stack allocations.
We implemented `bounded_worker_threads`, which reads available system parallelism and clamps the worker
thread count between 1 and 8 (`MAX_RUNTIME_WORKER_THREADS = 8`).
This keeps scheduler overhead bounded, minimizes context switching, and leaves CPU capacity available
for compiler jobs and IDE tasks on developer machines."

Q7: "Explain how you use `tokio::task_local!` to propagate security context safely."
Answer:
"In an asynchronous, multi-threaded framework like Axum, tasks can yield at `.await` points and resume
on different OS threads. Storing authentication context in thread-local storage (`thread_local!`) would
lead to race conditions and corrupted user attribution.
Instead, we define a `tokio::task_local!`:
```rust
tokio::task_local! {
    static REQUEST_DATA: RequestData;
}
```
During HTTP authentication or stdio frame ingestion, the middleware resolves the `AuthUser` or `BotIdentity`
and initializes the task-local scope using `REQUEST_DATA.scope(data, async { ... })`.
Any downstream MCP tool execution can synchronously call `REQUEST_DATA.with(|d| ...)` to retrieve the verified
caller identity. This guarantees zero-race, cryptographically sound caller attribution with zero parameter
drifting."

Q8: "How does the surgical string replacement in `edit_issue` handle concurrency conflicts?"
Answer:
"The `edit_issue` tool takes `target_issue`, `old_string`, and `new_string`.
Inside an atomic SQLite transaction:
1. It reads the current description.
2. It verifies that `old_string` exists in the text.
3. Crucially, it asserts that `old_string` occurs exactly ONCE. If `old_string` appears multiple times,
   the operation fails with an ambiguity error, forcing the agent to provide more surrounding context.
4. If another agent or user modified the description in the interim such that `old_string` is no longer
   present, the transaction aborts with a mismatch error.
This provides optimistic concurrency control without requiring complex operational transformation (OT)
or CRDT algorithms, ensuring descriptions are never silently overwritten."

Q9: "Why is `CountAlloc` / custom allocator tracking important in your test suite?"
Answer:
"In `src/main.rs`, we declare:
```rust
#[cfg(test)]
#[global_allocator]
static TEST_ALLOCATOR: storage::test_alloc::CountingAllocator = ...;
```
When building high-performance systems in Rust, memory leaks or runaway heap allocations (e.g., repeatedly
cloning large strings inside serialization loops) can slip past standard unit tests.
Our custom counting allocator monitors heap allocations during test execution, asserting that operations
like reading paginated issues or executing MCP tool dispatches remain strictly within predictable memory
budgets and zero-unnecessary-clone constraints."

Q10: "How do you handle SIGPIPE in piped CLI output when streaming large datasets?"
Answer:
"When a user runs a CLI command like `backlogbridge-mcp issue list --json | head -n 5`, the downstream
program (`head`) consumes 5 lines and immediately closes the pipe.
In standard Unix systems, writing to a closed pipe raises a `SIGPIPE` signal, which terminates the process
abruptly without running destructors or closing database handles cleanly.
In `src/main.rs`, we configure Unix signal handling to explicitly ignore default `SIGPIPE` termination,
allowing Rust's `std::io::Write` to return an `Err(ErrorKind::BrokenPipe)` instead.
The CLI catches this error gracefully, flushes stdout, and exits with code 0 without triggering database
lock corruption or leaving dangling temporary files."

GROUP C: DATABASE INTERNALS, STORAGE & WAL SEMANTICS
----------------------------------------------------------------------------------------------------

Q11: "Explain how SQLite's WAL mode works and why it allows concurrent reads during writes."
Answer:
"In traditional rollback journal mode, writing to SQLite requires an exclusive lock on the entire database
file; readers cannot read while a writer is writing, and writers cannot write while readers are reading.
In Write-Ahead Logging (WAL) mode (`PRAGMA journal_mode=WAL;`):
1. Modifications are not written directly to the main database file (`.db`). Instead, changes are appended
   to a separate write-ahead log file (`.db-wal`).
2. Because writes are append-only to the WAL file, readers can continue reading consistent historical
   snapshots from the main database file and committed portions of the WAL simultaneously.
3. Readers never block writers, and writers never block readers.
4. Periodically, or when the WAL reaches a threshold (default 1000 pages), SQLite executes a checkpoint
   operation, transferring committed WAL transactions back into the main database pages."

Q12: "How did you design the database connection pool in `src/db/mod.rs` to prevent `SQLITE_BUSY`?"
Answer:
"SQLite allows multiple concurrent readers in WAL mode, but strictly ONE writer. If multiple threads
attempt to write simultaneously, SQLite returns `SQLITE_BUSY`.
Rather than relying on SQLite's internal busy handler with exponential backoffs, we solved this
architecturally via Read/Write Splitting:
- The `DbPool` holds exactly one writer connection wrapped in an `Arc<Mutex<rusqlite::Connection>>`.
  Any write operation must acquire this mutex in Rust code. Because mutex acquisition is FIFO-ordered
  by the OS scheduler, write contention is resolved cleanly in memory; two threads never attempt to write
  to SQLite at the exact same instant.
- The `DbPool` maintains an `Arc<ArrayQueue<rusqlite::Connection>>` of 8 dedicated read-only connections.
  Read queries acquire a reader from this lock-free queue, execute, and return it upon drop via an RAII
  guard (`ReadConn`).
- This design completely eliminates `SQLITE_BUSY` errors while maximizing read parallelism."

Q13: "How does BacklogBridge-MCP implement online hot backups without locking the database?"
Answer:
"We utilize SQLite's native Online Backup API via `rusqlite::backup::Backup`.
1. The backup engine creates a target backup database file.
2. It initializes an online backup session between the source and target databases.
3. It copies pages in small, configurable batches (e.g., 50 pages per step).
4. Between steps, SQLite briefly yields locks so ongoing application write transactions can proceed
   uninterrupted.
5. If a writer modifies a page that was already copied, SQLite's backup engine detects the dirty page and
   re-copies it before completing the snapshot.
6. The resulting snapshot is guaranteed to be transactionally consistent and uncorrupted, achieved with
   zero downtime and zero blocking of active MCP agents."

Q14: "Why did you use integer sequence numbers (`sync_seq`) instead of timestamps for sync?"
Answer:
"Wall-clock timestamps (`created_at`, `updated_at`) are dangerous in distributed and concurrent systems
due to clock drift, NTP adjustments, leap seconds, and virtualization time jumps. Two operations occurring
on different cores within the same microsecond can have identical or reversed timestamps.
We introduced `sync_seq`, a monotonic 64-bit integer backed by an SQLite sequence generator.
Every mutating transaction increments `sync_seq` by 1.
This provides a strictly ordered, discrete timeline of all events across the entire instance. Reconnecting
clients simply send `last_seen_seq`, and the server returns all delta mutations where `seq > last_seen_seq`,
guaranteeing complete, gapless event replay."

Q15: "How does the project archive import/export prevent starving everyday database operations?"
Answer:
"Exporting or importing an entire project involves packaging hundreds of issues, comments, revisions,
and multi-megabyte binary attachments into a `.tar.gz` archive. This is an I/O and CPU-intensive workload.
If an archive operation were allowed to grab normal database connections, it could starve interactive
agent queries.
In `src/db/mod.rs`, we established isolated semaphore budgets:
- General queries use standard read slots.
- Issue and page exports share an `export_slots` semaphore.
- Whole-project archives must acquire an exclusive `archive_slots` semaphore (`tokio::sync::Semaphore`).
  Only ONE project archive operation is permitted per instance at any time.
If another archive request arrives, it is immediately rejected with HTTP 429 (Too Many Requests) before
allocating memory or touching temporary files, protecting database responsiveness."

GROUP D: SECURITY, CRYPTOGRAPHY & ACCESS CONTROL
----------------------------------------------------------------------------------------------------

Q16: "Explain the threat model for AI agent API keys and how bot identities solve attribution."
Answer:
"Threat Model: If multiple AI tools (Cursor, Claude Code, CI bots) share a single master API key or human
credential:
1. Revocation Blast Radius: Revoking an compromised key breaks all active agents and the human's access.
2. Loss of Auditability: When an issue is deleted or code is marked done, there is no way to know whether
   the human user did it, Claude Code did it, or Cursor Composer did it.
Our Solution: Bot Identity Minting.
When an AI client connects via `backlogbridge-mcp connect`:
- The system mints a unique, scoped Bot Token bound specifically to that tool (e.g., `cursor-agent`).
- The Bot Token is cryptographically tied to the authorizing human user (`owner_user_id`).
- All actions taken by that token record the exact actor metadata: 'Cursor (via Gopi Rk)'.
- If one tool behaves erratically, its token can be revoked instantly without affecting any other agent
  or the human's login session."

Q17: "Why do you use constant-time string comparison for token validation?"
Answer:
"Standard string comparison (`==` or `strcmp`) returns `false` immediately upon discovering the first
mismatched byte.
An attacker measuring network response latency with high-resolution timers can determine how many leading
bytes of an API key were correct, because each correct byte adds measurable nanoseconds to the comparison
time before failing. This allows brute-forcing a 64-character token in linear time ($256 \times 64$) rather
than exponential time ($256^{64}$).
We use the `subtle::ConstantTimeEq` crate:
```rust
token_hash.ct_eq(&expected_hash).into()
```
This forces the comparison loop to evaluate every byte regardless of mismatch location, completely
neutralizing timing side-channel attacks."

Q18: "How does the OAuth 2.0 Device Authorization Grant (RFC 8628) work for terminal AI tools?"
Answer:
"AI agents and developer CLIs often run in headless environments or terminal windows where opening a
browser callback redirect (standard OAuth authorization code flow) is impossible.
BacklogBridge-MCP implements RFC 8628 (Device Flow):
1. The CLI calls `POST /oauth/device/code` with its client ID.
2. The server responds with a `device_code`, a user-friendly `user_code` (e.g., `WDJB-TVKC`), and a
   verification URI (`http://localhost:3456/device`).
3. The CLI displays the URI and code to the developer and begins polling `POST /oauth/device/token`.
4. The developer opens the URL on their machine and clicks 'Approve'.
5. On the next poll, the server issues a scoped access token to the CLI.
This allows terminal-based agents like Claude Code to authenticate securely without sharing master
passwords or managing raw API keys manually."

Q19: "Why is Argon2id preferred over bcrypt or PBKDF2 for human password storage?"
Answer:
"Argon2id (the winner of the Password Hashing Competition) is superior because it is both compute-hard
and memory-hard:
- PBKDF2 and standard SHA algorithms are purely compute-bound; they can be cracked at billons of guesses
  per second using modern GPU clusters or custom ASICs.
- bcrypt is memory-limited to an ancient 4 KB state, which still fits inside the fast L1 cache of modern
  FPGA and GPU cracking rigs.
- Argon2id requires significant configurable RAM (e.g., 64 MB) and multiple passes to compute each hash.
  Because GPUs possess limited fast local memory per core, memory-hard algorithms destroy GPU parallelization,
  rendering brute-force attacks economically and computationally unfeasible."

Q20: "How do you securely handle sensitive credentials in memory during execution?"
Answer:
"Sensitive data (plaintext passwords, unhashed bearer tokens) is protected using the `zeroize` crate.
When sensitive string structures are dropped, their memory buffers are not merely deallocated (which leaves
the raw bytes intact in RAM until overwritten); they are explicitly overwritten with zeroes.
This mitigates memory disclosure vulnerabilities, such as memory dump extraction, use-after-free bugs,
or cold-boot attacks against host RAM."

GROUP E: PERFORMANCE, TOKEN ECONOMICS & PRODUCTION HARDENING
----------------------------------------------------------------------------------------------------

Q21: "How do you protect WebSocket endpoints against Slowloris and connection exhaustion attacks?"
Answer:
"In `src/realtime.rs`, we implement five concentric layers of defense:
1. `SOCKET_SEND_TIMEOUT` (5 seconds): When broadcasting an event, if an outbound socket's kernel buffer
   fills up because the client is intentionally reading slowly, the write future times out after 5 seconds
   and terminates the connection, releasing its socket permit and memory buffers.
2. Bounded Tungstenite Limits: Frame size is capped at 4 KB and message size at 16 KB, preventing attackers
   from allocating large memory chunks during protocol decoding.
3. Message Frequency Rate Limiting: Clients are restricted to 64 messages per 10-second window. Exceeding
   this triggers immediate disconnection.
4. Per-User Quotas (`MAX_SOCKETS_PER_USER = 16`): A single compromised or malfunctioning client account
   cannot open more than 16 concurrent WebSockets.
5. Instance-Wide Cap (`MAX_SOCKETS_TOTAL = 1024`): Clamps total system descriptors to guarantee file
   descriptor and worker thread availability for critical HTTP and MCP traffic."

Q22: "Explain the memory and token advantages of `get_briefing` over querying multiple endpoints."
Answer:
"When an AI coding agent resumes work, a naive workflow calls 5-8 separate tools: `list_projects`,
`list_issues`, `get_board`, `list_comments`, `get_page`.
This incurs multiple round-trips (hundreds of milliseconds of latency) and returns verbose JSON payloads
that consume 15,000+ tokens of context.
`get_briefing(project="CORE")` executes a consolidated database query that aggregates:
- Active milestone objectives and roadmap goals.
- Unblocked 'workable' issues ready for implementation.
- Critical blocked issues and what they are waiting on.
- Key architecture documentation links.
- Summary of changes since the agent's last active timestamp (`since`).
It formats this entire project status into a compact, human- and LLM-optimized summary of roughly
6,000 characters (~1,200 tokens). The agent gains complete project awareness in a single round-trip,
saving over 85% of resumption token costs."

Q23: "How does the asset embedding system (`rust-embed`) work at compile time and runtime?"
Answer:
"Rather than requiring the server to look up HTML, CSS, and JS files from a local directory on disk at
runtime (which fails if files are moved, requires directory configuration, and incurs filesystem latency),
we use `rust-embed`:
1. During `cargo build`, Vite builds the Svelte 5 frontend into `web/dist/`.
2. The `rust-embed` procedural macro reads every file in `web/dist/` at compile time and bakes its raw
   bytes directly into the binary's `.rodata` (read-only data) executable segment.
3. At runtime, when a browser requests `/` or `/assets/index.js`, Axum queries the embedded asset table.
4. Files are served directly from RAM with pre-computed MIME types and gzip/brotli compression headers.
5. The result is zero disk I/O, instant 0.1ms asset serving, and a truly self-contained single binary
   that can be moved anywhere without accompanying asset directories."

Q24: "What happens if a developer's machine loses power during an active SQLite write?"
Answer:
"Data integrity is completely preserved:
1. SQLite WAL mode writes transactions sequentially to the `.db-wal` log file.
2. A transaction is only considered committed once its commit record is synced to disk via `fsync` (or
   operating system flush).
3. If power fails mid-write, the incomplete transaction in the WAL file lacks a valid commit frame.
4. Upon reboot, when BacklogBridge-MCP opens `backlog.db`, SQLite detects the WAL file, rolls forward
   all valid committed transactions, and automatically discards the truncated, uncommitted frame.
5. The database returns to the exact consistent state of the last committed transaction with zero page
   corruption."

Q25: "How would you scale BacklogBridge-MCP from a single developer to a 500-person enterprise?"
Answer:
"Scaling is approached systematically across three tiers:
1. Vertical Compute Optimization (Up to 100 Concurrent Agents):
   - BacklogBridge-MCP's single-binary Rust engine is already capable of handling over 2,000 queries per
     second on an 8-core, 16GB RAM VPS because SQLite runs in-process with sub-millisecond query execution.
   - Attach high-performance NVMe storage to maximize WAL checkpoint throughput.
2. Read Replicas via Litestream / LiteFS:
   - For geographically distributed engineering teams, deploy LiteFS (FUSE-based distributed SQLite)
     or Litestream.
   - Writes route to the primary instance, which continuously streams WAL frames to read replicas in
     Europe, Asia, and North America, delivering sub-millisecond local reads globally.
3. Multi-Project Tenant Sharding:
   - Because issue tracking is inherently project-scoped (Project A has no relational joins with Project B),
     instances can be sharded horizontally per engineering organization or repository, maintaining the
     operational simplicity of self-contained SQLite instances while scaling horizontally to thousands of
     concurrent users."
